## ⚠️ БЕЗ СПОЙЛЕРОВ ДИЗАЙНА
Доменную модель (схему БД, связи) **проектирую САМ, даже криво.** Кривая-но-моя > правильная-от-тебя.
- Можно (не спойлер): **механика инструмента** — «как работает hasMany / pivot / FK / миграции».
- Нельзя (спойлер): **дизайн МОЕЙ модели** — «как структурировать списки/товары/магазины».
- Линия: КАК работает тул — спрашиваю; КУДА его приткнуть в моей модели — решаю сам.
- Ревью — через **вопросы-сценарии** («что будет, если два юзера…»), чтобы фикс нашёл я.
- Калибровка: мучаюсь на ДИЗАЙНЕ; спрашиваю на МЕХАНИКЕ-пробелах.

## Проект
**Домен:** список покупок, **многопользовательский** (я, жена, мама…), чтобы не забывать купить.
- Главная плоскость — **список СПИСКОВ** (не товаров); товары живут внутри списков.
- Магазины (shops).
- **Категории — пока НЕ решено (намеренно).** На старте вообще без категорий. Модель категорий «резиновая»,
  будет решаться ПО МЕСТУ по мере реального использования — варианты в голове: per-user / общие от админа
  (у меня будет 2 аккаунта: юзерский + админский) / «динамические» (категория одного юзера становится
  доступна остальным). НЕ спойлерить решение — это как раз тот дизайн, что проектирую сам.
- (Всю схему проектирую сам — см. «без спойлеров».)

**Это боевой v1** (им реально буду пользоваться), а НЕ песочница. Чистая архитектура с дня 1,
best practices сразу (Policy/Form Request), без намеренных дыр.
