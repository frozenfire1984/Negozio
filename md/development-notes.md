# Negozio — заметки по разработке

Итоги вспомогательной сессии, 25 октября 2026 года. Это контекст и учебные заметки, а не список уже реализованных требований. Процесс покупки описан отдельно в [shopping-flow.md](shopping-flow.md), устройство шаблонов — в [BLADE_GUIDE.md](../docs/BLADE_GUIDE.md).

## Формат работы

Юрий пишет код и выполняет команды самостоятельно. Ассистент объясняет механику, помогает разбирать ошибки и ревьюит по запросу. Не раскрывать заранее остальные ошибки учебного кода, если пользователь намерен найти их сам. Изменения Git разбирать пошагово: команда → результат пользователя → следующий шаг. Документация в этой заметке сохранена по отдельному запросу пользователя.

## Шаблоны и стили

- Публичная оболочка — `resources/views/layouts/site.blade.php`, связанная с `<x-main-layout>` через `app/View/Components/SiteLayout.php`. Пользователю понятнее хранить оболочки в `layouts`, даже при необходимости небольшого класса компонента.
- `layouts/app.blade.php` обслуживает кабинет, `layouts/guest.blade.php` — страницы авторизации. Название `guest` не означает всю публичную часть сайта. Авторизация пользователя сама по себе не означает наличие роли администратора.
- Публичные стили собираются из `resources/css/site/index.scss`; кабинет и авторизация сохраняют отдельные стили Tailwind.
- Обсуждались вложенные лейауты для колонок и именованные слоты для дополнительных областей. Это возможности, а не обязательная будущая структура.
- Sass `@use` изолирует зависимости: миксины, подключённые в оркестраторе, не становятся доступны другим partials автоматически. Каждый использующий файл подключает инструменты сам; `as *` позволяет вызывать их без префикса. Обсуждалось неудобство этого подхода для наброска и возможность временно держать стили в одном файле. Окончательное решение об организации не фиксировалось.
- Для значений и тем пользователь предпочитает нативные CSS-переменные. Обсуждались `color-mix()` с чёрным для затемнения и с `transparent` для прозрачности.
- Для интерфейса выбран Inter, подключение через Google Fonts. При переходе с Tailwind на обычный CSS отдельно нужен осознанный выбор базовых стилей/reset; конкретный reset в этой сессии не внедрялся.

## Инцидент с созданием магазина

При копировании `ShopController` в нём остались обращения к `ShoppingList`. Отправка формы магазина создала список покупок вместо магазина:

- `name` подходил обеим сущностям;
- `user_id` явно передавался кодом контроллера через `auth()->id()`, а не автоматически подставлялся Eloquent;
- `mode` имел значение по умолчанию;
- `display_name` и `address` отсутствовали в `$fillable` модели `ShoppingList` и молча отбрасывались до SQL. Поэтому ошибки несуществующих столбцов не было.

Пользователь включил в `AppServiceProvider::boot()`:

```php
Model::preventSilentlyDiscardingAttributes(
    $this->app->isLocal()
);
```

Повторная отправка формы дала ожидаемое `MassAssignmentException`. Затем пользователь самостоятельно исправил контроллер; создание магазина заработало. При чтении текущего кода 25 октября обращения в `ShopController` уже использовали `Shop`; полного ревью исправленного CRUD не проводилось.

Проверка сейчас включена только локально. Включение на всех окружениях обсуждалось, но не реализовано в рамках сессии. С `APP_DEBUG=false` необработанное исключение даёт пользователю обычный ответ 500 без трассировки; собственный шаблон ошибки можно хранить в `resources/views/errors/500.blade.php`.

Название контроллера не ограничивает доступные ему модели. Валидация, `$fillable`, policies и ограничения БД защищают разные аспекты, но могут пропустить логически неверную запись, если она допустима по всем этим правилам. Полезная проверка такого инцидента: POST создания магазина увеличивает число магазинов, не меняя число списков. Тест в этой сессии не добавлялся.

## POST, повторная отправка и PRG

- Обновление страницы ошибки после POST может повторить запрос с теми же данными формы. После исправления контроллера такой повтор уже выполняет новый код. Старый запрос не продолжает работу и данные не «доезжают» сами.
- После успешного создания, обновления и удаления использовать Post/Redirect/Get: изменение → redirect → GET страницы результата.
- GET-запросы не должны изменять данные. Показ страницы подтверждения удаления допустим через GET; само удаление выполняется отдельным запросом.
- PRG предотвращает повтор операции при обычном обновлении конечной страницы, но не гарантирует защиту от двойного клика, сетевых повторов и конкурентных запросов.
- Для текущего этапа достаточно PRG и ограничений БД по смыслу данных. Одинаковые названия магазинов/списков не обязательно являются запрещёнными дублями. Ключи идемпотентности пока не внедрять без конкретной потребности.
- Вопрос повторного создания списков из отложенных товаров при завершении покупки остаётся отдельным доменным требованием из `shopping-flow.md`; обсуждение PRG его не отменяет.

## Имя, версия и футер

- Имя приложения задаётся через `APP_NAME` в `.env`; `env('APP_NAME', 'Laravel')` в `config/app.php` читает переменную, второй аргумент — запасное значение. После изменения при необходимости очистить кеш конфигурации.
- Смена `APP_NAME` может сменить стандартное имя cookie сессии и привести к выходу из авторизации. Это зависит от настройки `session.cookie`/`SESSION_COOKIE`, а не является следствием любого изменения `.env`.
- В `config/app.php` пользователь добавил `'version' => '0.1.0-dev'`, вывод версии планируется/используется через `config('app.version')` в футере. Версию удобно хранить вместе с кодом в Git.
- Не повышать версию с каждой мини-фичей. `-dev` обозначает разработку будущего выпуска, `alpha` — ранний пробный выпуск, `beta` — стадию проверки основных возможностей. Границы alpha/beta определяются самим проектом.
- Ориентир первого пробного выпуска: связать списки с магазинами и добавить товары. Обсуждался переход к `0.1.0-alpha`; точный номер не является жёстким обязательством. Номер `0.1.0` не означает 10% готовности, переход сразу к `1.0.0` допустим.
- Пока стабильная `1.0.0` получает исправления `1.0.1`, `1.0.2`, будущая несовместимая версия может готовиться отдельно как `2.0.0-dev`. Большой размер фичи сам по себе не требует повышения major.
- Теги полезны для фиксации конкретных выпусков, но не нужны для каждого коммита. Тег указывает на коммит, не включает незакоммиченные изменения и не движется автоматически. `git tag v…` создаёт простой тег; `git tag -a v… -m "…"` — аннотированный. Создание локального тега само по себе не отправляет его на сервер.
- Допустим тег `v0.1.0-dev` как снимок этапа ради практики; факт его создания/публикации в этой заметке не утверждается.
- В футере достаточно имени и версии. Дополнительно можно позже показывать короткий хеш коммита, а на тестовом окружении — метку `TEST`. Это предложения, не реализованные изменения.

## Ветки и окружения

Большие фичи пользователь может разрабатывать в отдельных ветках. В будущем интересны прод, dev и, возможно, отдельное тестовое окружение как учебная практика.

Ветка и окружение — разные понятия. Обсуждалась простая схема: `feature/* → main → тестовое окружение → прод`, с доставкой на прод того же проверенного коммита. Постоянные ветки `dev`, `test`, `production` для этого необязательны. У окружений должны быть собственные настройки и базы данных.

Это пока направление развития, а не готовая инфраструктура или утверждённый план деплоя. Существующий план изучать Docker после рабочего v1 не отменялся.

### В план настройки сборки и деплоя

- Автоматически получать короткий хеш развёртываемого коммита через `git rev-parse --short HEAD` и показывать его в футере рядом с версией.
- Подставлять хеш после создания коммита, на этапе сборки или деплоя, через переменную окружения либо сгенерированный файл, не включаемый в Git. Не записывать хеш текущего коммита вручную в отслеживаемый файл: такая правка изменит сам коммит и его хеш.
- На тестовом окружении дополнительно показывать метку `TEST`. До настройки деплоя достаточно имени и версии приложения в футере. Механизм передачи метаданных сборки выбрать при реализации.

## Git: что делали и что выяснили

- Исправили неполный уже опубликованный последний коммит стилей: выборочно добавили SCSS и шаблоны публичной части/списков, выполнили amend и push с `--force-with-lease`. Изменения `ShopController`, `views/shops` и секцию Shop в `routes/web.php` оставили для отдельного коммита.
- Для переименования последнего коммита также подходит `commit --amend`; незакоммиченные изменения можно временно убрать в stash. Важно учитывать staging: обычный amend включает подготовленные изменения.
- `git stash` сохраняет изменения отслеживаемых файлов; `-u` также включает новые неотслеживаемые. `apply` сохраняет запись stash, `pop` удаляет её после успешного применения. `--index` пытается восстановить прежнее разделение staged/unstaged.
- Для изменения старого коммита обычно используют интерактивный rebase. `cherry-pick` переносит изменения выбранного коммита поверх текущей ветки, а не редактирует старый коммит на месте.
- Переписывание опубликованной истории обсуждалось в контексте личного репозитория. В совместной работе такие действия нужно согласовывать.
