# Процесс покупки — рабочая заметка

Это текущие договорённости, а не окончательная спецификация. Не всё описанное обязательно входит в v1. Код и доменную модель Юрий проектирует сам.

Технические заметки вспомогательной сессии (Blade/SCSS, инцидент ShopController, PRG, Git, версии и окружения): [development-notes.md](development-notes.md).

## Магазины: текущая стратегия (25 октября 2026)

- Магазины личные: у каждого магазина есть обязательный владелец `user_id`. Пользователь видит и выбирает свои магазины, изменяет и удаляет только свои.
- Это заменяет прежнюю идею общего каталога с фильтрацией по стране/городу пользователя. Страна и город могут оставаться сведениями о магазине, но не определяют доступ к нему.
- Одинаковый физический магазин может существовать отдельными записями у разных пользователей. Общий каталог сейчас не вводится.
- Для существующих записей выбран переход: добавить nullable `user_id`, вручную назначить владельцев, затем отдельной миграцией запретить `NULL`. Изменение схемы не заменяет фильтрацию запросов, Policy и проверки входящих ссылок на магазины.
- Группы пользователей (семья, друзья) и совместный доступ к магазинам и категориям — дальнейшая эволюция. Точную схему проектировать позже; сейчас поля и таблицы под группы не добавлять.
- Необязательная принадлежность магазина к бренду/сети — тоже на будущее; местный магазин может не иметь бренда.

### Удаление магазина и связь со списками

- Список может существовать без магазина. Удаление магазина не должно удалять списки покупок: их `shop_id` должен стать `NULL`.
- На странице подтверждения удаления нужно предупредить пользователя и показать, какие списки останутся без магазина.
- Намеченный механизм БД — внешний ключ с `ON DELETE SET NULL` (`nullOnDelete()`); это план, а не отметка о выполнении.
- Учебный порядок: сначала самостоятельно добавить выбор магазина в формы списков, сохранение и отображение связи; затем попробовать удалить привязанный магазин и увидеть отказ внешнего ключа. Только после этого менять ограничение новой миграцией и проверять разницу.
- При текущем ограничении и включённых внешних ключах удаление привязанного магазина отклоняется; без обработки исключения пользователь увидит ошибку. Пока связи не заполнены (`shop_id = NULL`), этот сценарий не воспроизводится.
- После изменения проверить: магазин удалён, связанные списки сохранились, их `shop_id` равен `NULL`.

### Удаление аккаунта — незавершённый сценарий

- Желаемое поведение: вместе с пользователем удаляются его личные списки и магазины; ничейными они оставаться не должны.
- Судьбу товаров при удалении списка и порядок удаления зависимостей ещё нужно определить. Согласовать всю цепочку внешних ключей перед включением каскадов.
- Отдельно проверить существующее удаление своего аккаунта через профиль Breeze. Полноценная реализация этого сценария пока отложена.
- Супер-администратор и `is_super_admin` обсуждались как возможное развитие, сейчас не являются реализованным механизмом доступа.

## Состояния списка

| Статус | Значение |
| --- | --- |
| `draft` | Список составляется, ещё не утверждён. |
| `future` | Покупка запланирована на будущее; дата необязательна. |
| `ready` | Список утверждён: можно идти в магазин. |
| `active` | Покупатель собирает товары в магазине. |
| `checkout` | Сбор закончен, покупатель идёт к кассе или оплачивает. |
| `done` | Покупка завершена после оплаты, редактирование запрещено. |
| `archived` | Архивный список, редактирование запрещено. |

Основной сценарий:

`draft → ready → active → checkout → done → archived`

Точные переходы для `future` пока не определены.

## Режимы списка

- Отдельное поле `mode` определяет доступные действия в интерфейсе, независимо от `status`.
- `simple` — простой режим по умолчанию: минимум кнопок, использование как обычного списка с возможностью быстро завершить покупку.
- `advanced` — расширенный режим с кнопками полного процесса покупки. Прохождение всех этапов всё равно не обязательно: экспресс-завершение доступно.
- Простой режим нужен, чтобы не перегружать новых пользователей, в частности жену и маму.
- Позже дефолт можно поменять на расширенный режим. Изменение дефолта само по себе не меняет режим существующих списков.
- В архиве режим не влияет на отображение и доступные действия. Сбрасывать сохранённое значение для этого не требуется.
- При копировании архивного списка ещё предстоит решить: наследовать режим исходного списка или использовать текущий дефолт.

## Состояния товара

| Статус | Значение |
| --- | --- |
| `idle` | Товар ещё не взят. |
| `in_cart` | Товар положили в корзину, но ещё не оплатили. |
| `deferred` | Покупку отложили; при завершении товар будет скопирован в новый список. |
| `canceled` | От покупки товара отказались. |
| `bought` | Товар оплачен. |

## Поведение

- Пользовательские кнопки называются понятными житейскими фразами; внутренние статусы знать не нужно. Формулировки кнопок пока предварительные.
- Утверждение списка переводит его в `ready`, начало покупок — в `active`.
- Кнопка «Иду к кассе» проверяет оставшиеся `idle` и предупреждает о забытых товарах. Покупатель может добрать их или отменить. Точный порядок проверки и перехода в `checkout` ещё предстоит определить.
- В `active` и `checkout` можно добавлять спонтанные покупки: например, интересный товар в торговом зале или жвачку у кассы. Это позволяет сохранить покупку в истории, даже если её не было в первоначальном плане.
- Спонтанно добавленный в `active` или `checkout` товар сразу получает статус `in_cart`.
- `is_unplanned` — отдельный булев признак внеплановой покупки, независимый от статуса, по умолчанию `false`. В интерфейсе такие товары должны отличаться от запланированных.
- `is_priority` — булев признак приоритета, по умолчанию `false`. Сценарий: до закрытия магазина мало времени, нужно выделить самое важное. Приоритетные товары можно показывать первыми и визуально выделять.
- В `checkout` можно отменять товары. Например, шоколадку не удалось купить на кассе — её можно отменить до завершения покупки.
- При подтверждении «Оплатил, готово» список переходит в `done`: товары `in_cart` становятся `bought`, оставшиеся `idle` становятся `canceled`, отменённые остаются отменёнными.
- Из списка можно выйти в любом состоянии. Сам выход не означает завершение покупки.
- Можно пользоваться черновиком как простым списком и отмечать товары, не проходя все состояния списка. Детали такого режима пока не определены.
- Экспресс-завершение: из любого незавершённого состояния (`draft`, `future`, `ready`, `active`, `checkout`) можно сразу перейти в `done` без промежуточных этапов и без предупреждения о забытых товарах. Это полезный сценарий для v1. Из `archived` переход в `done` недоступен; список в `done` уже завершён.
- При экспресс-завершении действует общее правило завершения: `in_cart → bought`, `idle → canceled`, отменённые остаются отменёнными. После перехода в `done` редактирование запрещено.
- В `done` и `archived` редактирование запрещено. Любой из этих списков можно скопировать в новый: все товары независимо от исходного статуса получают `idle`, исходный список сохраняется.

## Отложенные товары

- До завершения покупки любой товар можно перевести в `deferred` и обратно. Конкретный статус возврата пока не уточнён.
- При завершении покупки автоматически, без вопроса «да/нет», создаётся новый список с именем «Из отложенного <дата>», если есть товары `deferred`.
- В новый список копируются отложенные товары со статусом `idle`.
- В исходном завершённом списке эти товары остаются со статусом `deferred`, сохраняя историю. Правило действует и при экспресс-завершении.
- Возможна реализация через очередь, но способ пока не выбран. Повторное выполнение завершения не должно создавать дубли списков.

## Необязательные сведения о товаре

- Количество и вес необязательны. Для веса обсуждено хранение в килограммах с тремя знаками после запятой (точность до грамма); единицу хранения следует явно зафиксировать. В SQLite объявление `DECIMAL` не гарантирует точную десятичную арифметику.
- `price` — фактическая сумма за всю позицию, `estimated_price` — предполагаемая сумма. Оба поля необязательны; это пока не полноценная бухгалтерия.
- Одна `currency` хранит трёхбуквенный код валюты для обеих сумм позиции. Предполагаемая и фактическая суммы трактуются в одной валюте.
- Валюта автоматически подставляется из настроек пользователя, вводящего цену, и сохраняется вместе с суммой. Её можно изменить через дополнительное действие в форме. Изменение страны или настроек не меняет валюту старых покупок.
- Начальный справочник валют может быть небольшим: `RUB`, `RSD`, `EUR`. Конвертация и выбор курса отложены; исходная сумма сохраняется в исходной валюте.

## Фотографии — дальнейшее развитие

- В v1 фотографий не будет. Сценарии на будущее: показать другому покупателю нужную упаковку и сохранить фото удачной покупки для истории.
- Файлы хранятся в хранилище, в базе — пути к ним.
- Выбран учебный вариант: основное фото в `photo_path` товара, дополнительные — в отдельной связанной таблице. При удалении основного путь дополнительного переносится в товар, а запись дополнительного удаляется; сам продвинутый в основные файл сохраняется.
- При удалении товара его файлы тоже должны удаляться. Возможна отложенная очистка; механизм пока не выбран. Каскадное удаление строк БД само файлы не удаляет.
- Распознавание названия, цены и веса по камере, включая перевод граммов в килограммы, — дальний план.

## Совместный доступ и передача

- Для v1 список можно открыть одному другому пользователю. Групповой доступ отложен.
- `user_id` — текущий владелец списка, обязателен.
- `shared_user_id` — пользователь, которому открыт доступ, необязателен.
- При `editable_if_shared = false` доступ только для просмотра. При `true` разрешено редактировать товары, но менять статусы списка может только текущий владелец. Точные границы редактирования статусов товаров ещё нужно уточнить.
- Список можно передать другому пользователю: получатель становится владельцем, передавший получает совместный доступ с правом редактирования.
- `initial_owner_id` сохраняет первоначального владельца при передаче; до передачи может быть `NULL`.
- Повторная передача, возможно, будет запрещена. Это пока предварительное решение; запрет реализуется логикой приложения.
- Во время покупок пользователь с правом редактирования может удалённо добавить товар, например просьбу купить напиток. Такой товар получает `idle`, поскольку его ещё не положили в корзину.
- Для таких товаров планируется отдельный булев признак (рабочее имя `is_added_by_other_user`), чтобы визуально выделять их. Это отдельный признак от `is_unplanned`; их совместное использование ещё предстоит уточнить.
- Текущий замысел этого сценария — первоначальный владелец дополняет переданный список. Произвольные пользователи не могут добавлять товары, зная ID списка. Нужно согласовать это ограничение с общими правами совместного доступа.
- Обновления без перезагрузки через WebSocket — возможное дальнейшее упражнение, не обязательное требование для первой реализации.

## Напоминания о future

- При указанной дате хочется напомнить о запланированной покупке в нужный день.
- Без даты хочется напоминать о наличии будущих списков.
- Первый простой вариант — показывать напоминание при открытии приложения. Пока допустимы повторные показы без ограничения частоты.
- Web Push — возможное дальнейшее развитие, не обязательное для старта.

## Ближайшие планы: локализация интерфейса

- Добавить переключатель четырёх локалей: `ru` — Русский, `en` — English, `sr-Latn` — Srpski, `sr-Cyrl` — Српски. Это три языка и два варианта письменности сербского.
- Переводить кнопки, заголовки, сообщения и другие надписи интерфейса через языковые файлы Laravel.
- Предусмотреть сохранение предпочитаемой локали пользователя; точную реализацию выбрать при работе над локализацией.
- Английский интерфейс нужен в том числе для языкового погружения Юрия; другим пользователям нужен выбор языка.
- Пользовательские названия товаров, списков и другой введённый текст сохраняются в исходном виде, независимо от локали интерфейса.
- Автоперевод пользовательского текста — отдельный эксперимент на будущее, не часть ближайшей локализации. Исходный текст должен сохраняться.

## Отложенные вопросы

- Что делать со списками, оставленными в `ready`, `active` или `checkout` из-за пропущенных кнопок.
- Нужны ли автоматические переходы и автоархивирование, по каким признакам и через какое время. Решения пока нет; молчание пользователя не подтверждает оплату.
- Как и когда пользователь переводит `done` в `archived`.
- Точные переходы для запланированных списков и взаимодействие даты со статусом.
- Ограничение частоты напоминаний и пуш-уведомления.
- Возможный финансовый слой: учёт расходов. Пока это направление развития, а не требование к v1.
- Объединение и разделение списков — на будущее, правила пока не определены.
- Список дел с обычными задачами и задачами-походами, связанными со списком покупок, — дальний план. Это не третий режим `mode`; возможна отдельная таблица дел.

## Граница проработки сейчас

Сначала реализовать и проверить основной сценарий: составить список → собрать покупки → проверить забытое перед кассой → завершить покупку.

Не пытаться заранее закрыть все случаи пропущенных действий. Возвращаться к ним при реализации конкретного экрана и после реального использования. Автоматическое обслуживание заброшенных списков можно отложить.
